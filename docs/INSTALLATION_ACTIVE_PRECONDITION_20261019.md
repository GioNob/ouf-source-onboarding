# Conditional InstallationConfiguration lifecycle

An existing installation may be updated only against a strong owner-issued ACTIVE condition. `GET /api/trusted-human/v1/installations/{id}/active` retains installationId/revision/checksum and adds `generation`; its strong ETag is `"revision:checksum:generation"`. Generation counts append-only ACTIVATED, ROLLBACK_ACTIVATED and REVOKED lifecycle events for this installation. Returning to the same revision/checksum after rollback therefore never restores an older condition. No schema migration or deployment-specific value is introduced.

The existing `:activate`, `:rollback` and `:revoke` paths require `If-Match` with that exact ETag. Explicit absence for bootstrap uses `If-None-Match: *`; it cannot be mixed with If-Match. Missing condition is428, malformed/weak/list/overflow conditions400, stale condition412. Rollback additionally requires an older target revision. An ACTIVE row without corresponding lifecycle history cannot produce an admissible strong condition and needs reconciliation.

The owner checks the condition under the same installation-scoped PostgreSQL advisory transaction lock used for activation/revocation. A stale request cannot write ACTIVE or append transition events. HUMAN identity, capability, assurance, correlation and verified stateless bearer write proof remain mandatory. A precondition is neither authorization nor a replacement for native HUMAN/THS consent. These mutations remain excluded from MCP. Existing clients that omit preconditions now fail closed; historical completed actions must never be replayed to upgrade them.

Revision creation deduplicates the tuple installationId/actor/correlation under the installation lock. Reusing the tuple with the same canonical payload returns the immutable original revision, without a second VALIDATED event. A different payload is409; ambiguous historical duplicates are409 and require reconciliation. No raw credential, secret, client-supplied backend URL or SQL control path is introduced.

Environment validation refuses an outer transaction (`Propagation.NEVER`). Network probes run without a transaction or installation lock. Only after completion does a short transaction reacquire the installation lock, recheck immutable payload checksum and revocation, and append the validation evidence. Revocation can complete while a probe is pending, and wins over its later PASS result. A caller holding an outer transaction is rejected before any probe.

# Managed source review from chat

This change continues the existing managed-file, owner approval and OAuth2 Trusted Human Surface. It does not change who may approve, publish or activate.

The authenticated HUMAN delegated by MCP may call `source.onboarding.review.prepare` with the existing source ID, onboarding version UUID, exact lock version and stable command key. An optional [execution proposal](MANAGED_FILE_EXECUTION_PROPOSAL.md) completes the existing draft using owner-held file metadata and explicit published semantic/UDP policy pins. The owner validates and freezes the configuration, creates one approval challenge and atomically retains its command fingerprint. The result provides the review URL and exact configuration hash. A repeated identical command reconciles that same challenge; a changed command or version conflicts. Expired challenges are not silently renewed.

`source.onboarding.read` checks current authority and file ownership before returning state, frozen hash, challenge status, publication identity and Ingestion compatibility. These responses exclude file content, staging addresses and credentials. Authorization decisions retain their existing owner audit writes, including read requests.

The browser routes `/trusted-human/onboarding/` and `/trusted-human/semantic/` share the existing `ouf-ths` server session, PKCE and CSRF filter. Set `ouf.workflow.ths.gateway-base-url` to the same fixed Gateway origin used by the existing resolution surface and set `ouf.authorization.ths.public-origin` to the public HTTPS origin. No browser parameter chooses an upstream. Tokens remain server-side. Source decisions include the frozen configuration hash and expected lock version; semantic decisions include the reviewed content hash. Approval and activation/publication are explicit separate HUMAN actions. Reloading reconciles stored state and never submits a decision.

Source activation still requires the original Ingestion SERVICE compatibility attestation, exact source/version/hash and UDP governed identity gate. The new page does not manufacture either evidence or activation authority. MCP has no confirm, reject, publish or activate path. The runtime installation must register and grant the two explicit source capabilities through existing Authorization governance; deployment of code does not grant them.

After separate HUMAN approval, **Verifica e attiva** calls the real Ingestion readiness endpoint with the same HUMAN session. Ingestion reads the frozen owner version, verifies all rows with its actual runtime parser and published semantic references, then records its SERVICE compatibility attestation against the exact configuration hash. The owner next requests UDP identity preflight with the same HUMAN authorization and activates only through the original compatibility, current UDP coverage and publication gates. Activation makes the existing Ingestion publication poller eligible to start the run; this endpoint never inserts a run directly. No user token export or manual API sequence is required.

The activation path reuses `ouf.onboarding.udp-identity.gateway-url` for its fixed Gateway. The existing Onboarding SERVICE token remains necessary for the final UDP coverage read. New readiness/compatibility routes require their existing explicit HUMAN/SERVICE permissions; deployment of code alone grants nothing. `catalogue/chatbot-source-review-capabilities.json` declares the two source tools and the dedicated HUMAN semantic proposal-read capability, without role grants.

The versioned `managed-review-activation.v1` profile is interactive and bounded: prepare 10 seconds, read 3 seconds, ordinary browser owner calls 15 seconds and activation proxy 55 seconds. One explicit activation request runs at most one Ingestion probe (35-second client deadline), one UDP preflight (8 seconds) and the retained activation gate. Admission is limited to two concurrent attempts with no queue. Each frozen review retains its 60-second generation lease, attempt count and initial time across requests/restarts. Transient 408/429/502/503/504 and transport failures pause with 5/15/60/300/900-second backoff, up to20% jitter and Retry-After. Maximum128 attempts and24hours include attempt duration. Refresh shows phase, last code and next eligible time; resumption requires a new authenticated HUMAN click and fresh authorization, never a retained browser token or automatic replay of HUMAN intent. Integrity, revocation, stale configuration, unknown failures and exhausted budgets block.

Completed compatibility is read before another probe; exact-hash SERVICE POST is owner-idempotent under its source-version lock, including a lost acknowledgment. UDP preflight must likewise use its owner exact-hash deduplication. An ACTIVE owner publication is reconciled before any further dependency mutation, even if the previous activation response was lost. Final activation checks the same configuration hash, lock version and current generation. Network readiness calls occur outside database transactions; phase updates hold only short review-row locks. The original final UDP gate remains in the existing activation transaction. There is no new background scheduler or generic recovery framework. Automatic resumption without a current HUMAN session and HUMAN budget renewal after exhaustion are not implemented by this interactive profile; no claim of unattended outage recovery is made.

Tests cover the PostgreSQL lifecycle, one challenge across retries, stale-card rejection, fresh authorization denial, retained ownership/tenant, separate HUMAN approval, unchanged compatibility gate, fixed Gateway forwarding without bearer disclosure, content hash drift, closed arguments, session CSRF and browser state/reload behavior. Unit/CI HUMAN identities are fixtures, not VPS approval or end-to-end release acceptance. The integrated cohort run remains required before target acceptance. Additional tests exercise retained lease/budget fencing, Retry-After, exact-hash attestation reconciliation, malformed/drifting dependency evidence and the real HTTP sequence without an operator calling each backend.

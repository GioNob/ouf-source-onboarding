# Managed profiling recovery: persistent control permission profile

The recovery mechanism reuses the production V35 readiness model: immutable prior state, cumulative attempts, finite HUMAN session and a separate resume. The installed V36 source6ea5242f... already contains that engine. The subsequent access correction binds the native API to an owner-resolved `managed-profile-job`, following the exact-job authorization model used for Teatri UDP materialization recovery. This source correction is not a target deployment or policy publication.

The owner proves HUMAN identity, tenant/subject custody and the retained asset/job pair before constructing the resource. It publishes no state at that stage. The resource includes moduleONBOARDING, assetRef, jobRef and detailLevelTENANT_OPERATIONAL. This classifies the control metadata, not the CSV contents; no CSV dataAccessLabel is invented or changed. Current policy, scope, explicit DENY and ownership remain mandatory. New budgets do not repair missing permissions.

The packaged `authorization/managed-profile-recovery-role-v1.json` is an explicit role template consumed by the existing OufRoleCatalogue compiler. It contains no tenant, subject, assignment, validity, active grant, service principal or session. An administrator may merge it into a freshly read catalogue while preserving all other roles/assignments, choose an existing verified HUMAN assignment and explicit revocable validity, and submit that exact change through the existing HUMAN review. Missing active descriptors block compilation; the template never registers them or grants itself. No blanket capability-context grant or ordinary short grant renewal is introduced. A job-specific mandate can additionally constrain resourceId,assetRef,jobRef; the same profile works for subsequent owned jobs under a deliberately assigned structural role.

The template applies only to the managed-profile-job control context. It cannot authorize the older generic quarantine endpoint, CSV contents, raw logs, data-plane reads, another tenant or a service actor. Ownership is independently checked for every native recovery command. The native Gateway additionally checks its existing required scopes; a configured grant is not proof that a current token or route is valid. The existing MCP job-status path still needs its matching resource projection before this role can authorize that channel; do not infer that installation from this file.

Production regressions use the actual AuthorizationPolicy/LocalAuthorization and role compiler, rather than only mocked capability sets. They cover the legacy label-constrained role versus empty capability context, explicit assignment, exact job, wrong tenant/subject, missing scope/descriptor, expiry, sensitive data and explicit DENY. Real PostgreSQL proves resolution of the same retained owner/job without budget/event/state mutation. API regressions prove the two current capabilities before budget, and preserve denial for other jobs.

The recovery UI reports401, typed403, ownership denial and a bounded safe correlation separately. It does not render raw error details or automatically request another login for every403. An uncertain or denied mutation keeps the exact pending command across reload. Existing budget/resume separation and cumulative5→6–8 remain unchanged.

# Storage recovery platform binding — internal integration contract

This contract tightens the existing private owner boundary. It is not a new frozen PET
capability, a grant issuer, an endpoint, or an installed production adapter. Authorization
continues to own policy decisions; Gateway owns identity/routing; THS owns protected HUMAN
actions; platform operations owns backup/restore and writer custody. Existing per-file
profile recovery and installation configuration permissions are not reused for storage.

## Inputs and ownership

| Input | Trusted origin | Owner enforcement |
| --- | --- | --- |
| Installation reference | Protected installation configuration at worker startup | Exact match to evidence; no request/backup fallback |
| Runtime session | Fresh random UUID generated by `StorageRecoveryRuntime.start` | Exact authority and separate quiescence binding |
| Database incarnation | `pg_postmaster_start_time()` sampled at worker startup | Rechecked inside each owner transaction, before gate lookup |
| Current decision | Authorization/THS/platform integration, still to be installed | Existing action/scope/epoch/revocation/deadline checks |
| Quiescence | Current platform writer-custody verifier, still to be installed | Required for reconcile/freeze, bound to this runtime |
| Upload budget and history | Existing owner V39 intent | Same intent, key and durable128/24h limits across sessions |

The runtime object has a private constructor and no restore/deserialization constructor.
Create it once per worker lifetime. Do not persist or recreate its session from a receipt.
A new runtime is not permission to act and must not reset budgets or extend grant lifetime.
The owner cannot proceed without both the adapter and runtime. A fresh JVM rejects an old
projection even when that projection says unrevoked and has an unexpired deadline.

The future adapter must obtain current authority outside the owner recovery set and publish
only an authenticated, installation/action/epoch/runtime-bound decision into its locked
local projection. It must preserve the external decision/session identity and finite expiry.
It must not copy an old receipt, accept client JSON as proof, or automatically regrant after
restart. Rebinding an existing current decision is not a new budget. Recompute/verify writer
custody separately; an authority refresh does not extend an old quiescence assertion.

The platform still must implement a coordinated revocation/fencing protocol: an external
revocation must conflict with acknowledged local permissions and in-flight publication.
This patch does not claim that reading a remote decision once solves that race. The existing
same-transaction local gate locks, exact pre/post-GET binding checks and atomic audit remain
mandatory. External calls and waits stay outside owner transactions. Unknown/unavailable,
revoked, mismatched or expired decisions remain blocked, without renewal or blind retry.

## Restart and restore rules

1. A new process/worker creates a new runtime session and must obtain current attestation.
2. Evidence for another installation or runtime is denied before consuming the intent read
   budget or accessing S3. A matching authority session with old custody is also denied.
3. A worker that survives a physical PostgreSQL restart/restore detects the changed
   postmaster start time and refuses to continue. It must restart and reattest explicitly.
   Use a stable primary endpoint; failover to another postmaster also invalidates the binding.
4. FROZEN remains FROZEN. No session creation, authority refresh, restart or restored receipt
   grants reopening, advances the epoch, or resets the original intent budget.

This incarnation check addresses physical PostgreSQL restart/restore. A live logical data
rollback inside an unchanged postmaster requires a separate deployment-generation fence;
it is not qualified by this change. No production restore workflow is wired automatically.

## Native evidence and synthetic authority

Seven additional PostgreSQL cases cover absent runtime, stale runtime, wrong installation,
old custody after authority rebinding, exhausted budget across runtimes, persistent
revocation despite matching new bindings, and runtime replacement during GET. Existing
revocation, expiry, audit and concurrency cases remain required.

The physical fixture models current authority using a small test-only file outside every
owner export, recovered directory and restored data directory. This is not a production
policy service or a concurrent revocation implementation. Its adapter only rebinds an
existing current, unrevoked, unexpired decision; it does not renew time/session/budget.
The source projection is revoked after the named cut, together with that external decision.
PITR deliberately restores the old unrevoked row. A fresh JVM denies its old binding;
attestation against the current revoked decision, or a withheld current file, also fails.
The owner snapshot stays unchanged. Another JVM remains alive throughout database destruction
and restore, and must reject the changed postmaster before gate lookup.

The independent archive verifier binds the old/new runtime identities, unchanged read budget
on denied attempts, custody evidence after native S3 denials, audit sessions, post-cut local
revocation, current external-decision bytes, restored old projection and live-worker denial.
Semantic corruptions must be rejected even after recalculating ZIP checksums.

Production policy resource/capability registration, authenticated delivery, all-writer
custody, coordinated external revocation, denial audit, logical-restore fencing, UDP/Ingestion,
mixed rollout, reopening and representative RPO/RTO remain separate integration requirements.

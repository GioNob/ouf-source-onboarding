# Generic source property revision from chat

Candidate implementation; not deployed or accepted end to end. The runtime checkpoint remains technical8/8, functional4/6.

The owner composes its existing clone, CAS patch, full validation, freeze, native approval challenge and compatibility/activation coordinator. No application-specific source, field, class or priority is embedded in the implementation. Source kinds and scheduler configuration are retained; API/OGC sources use the same property-rule operation, while managed files retain their asset ownership check.

New independent capabilities `ouf.onboarding.revision.read` and `ouf.onboarding.revision.prepare` require explicit governed registration/grants and the corresponding HUMAN delegated scope. Preparation uses a separate purpose/path/body/capability bound owner receipt, MAC domain `ouf-source-revision-owner-v1.`; a managed-file or permission receipt cannot authorize it. The MCP workload holds no owner signing key and cannot approve or activate.

Read exposes an authorized property-rule projection and immutable version/hash/lock identity, not raw source values, staging locations or credentials. Prepare takes sourceId, parentVersionId, expectedVersion, configurationHash, stable commandKey, explicit publicationEffect=NEW_PUBLICATION_MAY_START_ACQUISITION and 1–256 exact (propertyIri,sourceField,reconciliation) changes. It requires the current ACTIVE parent and no unfinished source version. Unknown/duplicate/missing targets and no-op changes fail closed. Rules are validated by the existing full configuration validator, including temporal/deletion constraints. The previously developed XSD-string compatibility correction is incorporated without rewriting the original datatype.

Only selected reconciliation objects and generated bundle/extraction version references advance. All identity/key, semantic, authority, access, source asset, scheduling, delta and deletion configuration outside the selected rules remains unchanged. External explicit extraction-profile references require separate owner revision support; they are not silently rebound.

V34 is an additive append-only command journal. One transaction includes clone/patch/validate/freeze/challenge/review/journal; a failure rolls back the entire preparation. A source fence and tenant/subject/command fence serialize duplicate requests. The same command and fingerprint reconcile to the existing challenge, even after parent supersession; changed intent conflicts. No retry budget, login or challenge TTL is reset. There is no network request or wait inside preparation. Native activation shares the source fence and rechecks that the parent is still ACTIVE with the frozen hash before any publication.

THS displays the immutable base and publication effect: activating this revision publishes a new configuration of the same source and may start acquisition under its retained scheduler configuration, including a previously consumed managed file. Preparation itself does neither. Approval/activation and scheduler execution remain separate owner operations. Existing 128-attempt/24h readiness accounting and fencing are reused. No historical job or identity decision is replayed.

Qualification: preservation, API-source preparation, exact/concurrent replay, stale parent, changed intent, rollback on invalid policy, cross-tenant/subject/permission denial, native approval separation and MAC-domain/body/path binding tests are included. CI results must be recorded before rollout. Remaining integration: MCP manifest/transport and Gateway exact routes/schemas/materialization, policy registration, one qualified native deployment, concrete profile review/publication and stage5/6 runtime proofs.
